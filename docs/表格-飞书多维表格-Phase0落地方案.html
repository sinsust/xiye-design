表格 × 飞书多维表格 — Phase 0 落地方案

定位：把「AI 分析结论写回 Base（视图 / 分表 / 仪表盘图表）」跑通 · 范围收敛 · 基于 lark-cli base 真实能力

结论先行

飞书多维表格的强项是「数据组织 + 协作展示」，弱项是复杂计算。因此 Phase 0 采用Base 当真值源与展示容器我们把 AI 分析结论写回的姿势：重计算留在产品侧，Base 只承接写回的结果与可复用的上游数据。不试图把重分析搬进 Base，也不写永不落地的「统计字段」。

一、目标与范围

做（进 Phase 0）

  • 从 Base 读取 数据表 → 进入现有 ColumnProfile → AI 维度 → 分析。
  • 分析结论以三种真实可写回的载体落库：① 派生「分析结论」子表（记录）、② 原表持久化视图（筛选/排序/分组）、③ 仪表盘图表。
  • 写回做到幂等（可重跑不产生重复），重度应用侧计算只回写计算结果。

不做（明确排除）

  • 不实现「统计字段」持久化 —— 飞书聚合统计更适合用视图/仪表盘呈现，写回成字段会踩只读/重启重置的坑。
  • 不做 L2 双向增量同步、不做 L5 组织级权限/工作流（留待 Phase 1/2）。
  • 不在 Base 侧做复杂 OLAP 计算；那仍是产品侧职责。

二、数据流

Base 数据表→ 读记录（data-query / record-list）→ 产品侧 AI 分析→ 写回 Base→ 视图 / 子表 / 仪表盘

读路径走 lark-base 数据表查询与分析 SOP；写路径遵循「先读字段结构 → 只写存储字段 → 串行 + 冲突等待」。外部导入/导出（把本地上载表建成 Base、或把 Base 导出）转 lark-drive。

三、三种写回载体（对应命令面）

① 派生「分析结论」子表 — 推荐主路径

新建一张结果表，把每条 AI 结论/建议/行动写成一行的存储字段。最稳、最通用，且天然可被仪表盘读取。

动作lark-cli 示例
建结果表base +table-create --base-token <base> --name "AI分析结果" --fields '[...]'
写记录base +record-upsert / +record-batch-create（幂等用 upsert；单批 ≤200）
字段+field-create --json 创建 text / number / select / date / checkbox 等存储字段

② 原表持久化「分析切片」视图

把某次分析的过滤/排序/分组结果，沉淀成原表上的一个共享视图，供团队直接切过去看。

动作lark-cli 示例
建视图base +view-create（再补 filter/sort/group）
设筛选base +view-set-filter --filter-json '[...]'（tuple 条件结构见公共协议）
排序/分组/可见字段先 +view-get 读现状，仅替换目标项后写回（局部 delta）
视图适合「持久化、共享、UI 复用」；一次性筛选可先用 +record-list/+record-search 验证再沉淀为视图。

③ 仪表盘图表（读结果子表）

在 Base 仪表盘加图表组件，数据源引用「分析结论」子表，把 AI 结论可视化给团队。

动作lark-cli 示例
加组件base +dashboard-block-create（data_config 引 base_token + table，组件须串行创建）
排布+dashboard-arrange（服务端智能布局）
读图表结果+dashboard-block-get-data

四、字段类型映射

产品侧分析产出Base 字段类型写入约定
结论标题 / 建议文本text直接字符串

类别 / 结论分级select仅写已存在选项；先 +field-list / +field-search-options 确认，必要时先加选项

附件 / 原文文件attachment走 +record-upload-attachment，不作为普通记录字段写

硬规则：写入前必须先读目标表/字段结构；只写存储字段；formula / lookup / 系统字段 / 附件字段不作为普通记录写入目标。

五、幂等 · 并发 · 配额 · 权限规则

  • 幂等：写回优先用 +record-upsert，以「分析会话 id + 结论名」做业务键，重跑只覆盖、不新增；替代方案：同会话先删后插需显式确认。
  • 并发：连续写同一表必须串行；遇 1254291（写冲突）短暂等待后重试。
  • 配额：批量写 ≤200/批；多个字段创建按调用超时做时间预算拆分，而非固定条数。
  • 权限/身份：默认 --as user 操作用户资源；scope 或授权不足按「鉴权流程」恢复，不擅自降级 bot。权限模型与完整流程详见「权限模型」「鉴权流程」两节。
  • 只读降级：若凭证不支持写入，自动退化为「只读导入 + 本地分析」，写回入口置灰并给原因，不阻断分析主流程。

六、能力边界（提前知晓，避免返工）

当前不支持/受限

  • 视图的行高、冻结列、列宽等 UI-only 外观：lark-base 不支持，不做猜测参数或走裸 API。
  • 仪表盘组件不支持精确 x/y/w/h 与尺寸；只能用 +dashboard-arrange 自适应智能布局。
  • BaseApp（AppMode）的页面复制不支持；复制/克隆类需求直接说明并停止。
  • Base/Wiki URL 中 table= 只是「当前选中 block」，须以 +url-resolve 返回的 block_type 与 table_id / dashboard_id / workflow_id 为准，不按参数名当 table_id。
  • 统计/聚合：以「视图 + 仪表盘」呈现，不追求把聚合结果写成可写的持久字段。

七、权限模型

两种身份，两条授权通道

身份标识如何获得权限Phase 0 中的角色
user 用户身份 --as user 两层都必须满足：①开发者后台开通 scope；②用户本人 auth login 交互授权。 默认形态 —— 用用户自己授权读他自己的 Base、并写回他自己/团队能访问的 Base
bot 应用身份 --as bot 只需 appId + appSecret，在开发者后台开通 scope；禁止 auth login。 备用形态 —— 应用级/代理写入时考虑；看不到用户个人资源，写入告示、App 归属等
  • 身份是整条工作流的状态，不是单条命令的局部参数。某个 ID/结果经哪个身份取得，后续消费它就必须显式带相同 --as；禁止依赖 profile 默认身份“自动沿用”，也禁止遇到权限错误就切身份绕过。
  • Base 数据侧：权限先从 +base-get 读 owner/权限；高级场景（字段/记录粒度、角色）走 +advperm / +role。以 bot 创建 Base 时关注返回的 permission_grant，确认用户能否打开。
  • 三类失败必须区分处理：missing scope（完全没这个权限）、资源 ACL（有 scope 但对该条资源无权）、当前身份下不可见。恢复方式不同（见下表）。

八、鉴权流程

① 初始化（首用一次）

lark-cli config init --new 启动后取出授权链接，必须再转成二维码一并给用户【URL 视为不可修改的 opaque string】。

② 按最小权限发起授权（Phase 0 推荐，不要用 --domain all）

lark-cli auth login --scope "<base 读写所需 scope>" --no-wait --json

多次 login 的 scope 会增量累积；只授读 / 只授写要分开规划。生产上优先 --scope 精确授权，符合最小权限原则。

③ Agent 代理认证（split-flow，推荐给 AI 场景）

  • 发起：auth login --scope … --no-wait --json → 取 verification_url + device_code → 生成二维码给用户，本轮即结束交还控制权，不阻塞轮询。
  • 完成：用户回来告知已授权 → 由 agent 亲自执行 auth login --device-code <code>。不缓存验证 URL / device code，每次重新发起。

④ 状态 / 登出 / 撤销

可用 auth status --json --verify 看登录态、身份与 token 有效性；auth logout 只清本机登录态（服务端授权需用户在飞书授权管理页取消，CLI 不能单独撤销单个 scope）。

⑤ 权限不足时的恢复矩阵（Phase 0 写回最常遇到）

失败类型userbot
missing scopeauth login --scope <缺失scope>（推荐最小授权）把错误中的 console_url 给用户去开发者后台开通；禁止 auth login
资源 ACL（有 scope 但对这条资源无权）请求资源 owner 给当前用户授权请求 owner 给当前 app/bot 授权
当前身份不可见保持身份，如实报告不可见，不切身份重试同左

恢复完成后一律用触发错误时的原身份重试。错误响应里同时有 missing_scopes / console_url / hint，按提示走即可。

⑥ 安全护栏

  • 写回操作是高风险写：CLI 会触发 确认门禁（exit 10），须用户显式同意后追加 --yes；可用 --dry-run 预览请求，不擅自跳过门禁。
  • 禁止输出 appSecret / accessToken 明文；文件/输出路径只接受相对路径。
  • 判断调用成败用 ok == true（或退出码 0），不要用 code == 0——成功信封没有顶层 code。

九、里程碑与验收

里程碑内容验收标准
M1 读取打通 Base 数据表 → 产品分析 选一张 Base 表能拉到字段画像并进入现有 AI 维度流程
M2 结论子表写回 分析结论写入派生子表（upsert 幂等） 重跑 2 次两条结论，表中仍是 N 行不重复；字段值类型正确
M3 视图 + 仪表盘 沉淀切片视图 + 仪表盘图表 团队用 base 打开即可见结果视图与图表，读取依赖结果子表
M4 只读降级 凭证不达标的降级路径 无写权限时分析不中断，写回入口置灰并给出原因

风险：写权限/scope 配置、字段类型误映射、批量并发冲突；三者均已在第五节给出前置规则与降级路径。

权限边界、命令细节以 lark-base 各 reference 为准；字段 JSON / formula / lookup / 视图筛选 / dashboard data_config 在实现前逐一读取对应 SSOT。
