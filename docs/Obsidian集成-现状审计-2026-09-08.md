## 三、根因明细

### 根因 1：配置从未建立（决定性）

`user_obsidian_config` 0 行。没有 `vaultPath`、没有 `enabled=1`，于是：

- xiye → Obsidian 写回：`obsidian-sync.ts:25` 直接 `return`（拿不到 config）
- Obsidian → xiye 监听：`obsidian-watch.ts:44` 查不到 `enabled=1` 的行，一个 watcher 也不建

### 根因 2：watcher 没有启动钩子（架构缺陷）

`startObsidianWatch()` 的**全部**调用点只有两处，都在 API handler 内：

- `lib/api-handlers/brain/obsidian/config.ts:93`（PUT 保存配置时）
- `lib/api-handlers/brain/obsidian/sync.ts:26`（POST 手动同步时）

**不存在** `instrumentation.ts`，也没有任何 server 启动钩子。

后果：
1. dev server 每次重启 → 监听丢失，**必须**手动去 UI 点一次「保存」或「立即同步」才恢复
2. 模块级 `const watchers: FSWatcher[] = []`（`obsidian-watch.ts:19`）在 HMR 模块重载时也会丢
3. 当前 `localhost:3000` / `3001` 均无响应 —— dev server 根本没在跑

### 根因 3：vault 内容几乎为空

只有 1 个 `.md`。即使接通，双向同步也只能处理 `欢迎.md` 这一个文件，你自然感觉"没结合上"。

## 五、风险

| 级别 | 事项 |
|---|---|
| P1 | Windows 下 `fs.watch(dir, { recursive: true })` 可靠性一般，深层子目录变更可能漏报 |
| P2 | `startObsidianWatch` 多配置时，任一失败即整体 `return`，且已建立的 watcher 未清理 |
| P2 | 写回默认落在 vault **根目录**（`obsidianRelPath` 为空时），笔记多了会平铺一坨，无子目录归类 |
| P3 | 冲突策略为「最后写入优先」（.md mtime vs xiye updatedAt），双端同改会有一侧被覆盖 |
