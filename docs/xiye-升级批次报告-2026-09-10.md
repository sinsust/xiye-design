### before / after

**C1-a · 限流失败策略**
```
before:  if (error) { console.error(...); return true; }   // fail-open＝存储一挂，限流形同不存在
after :  if (error) { console.error(...); return memoryRateLimit(key, limit, windowMs); }
         ↑ 降级为单实例限流：不跨实例，但对「同源短时高频」滥用仍有效，且不误伤正常用户
```

**C1-b · API 鉴权**
```
before:  // API 请求：不重定向（未登录由路由自身返回 401 JSON），只负责刷新 cookie
         if (!user && !isApi) { redirect("/login") }
         return supabaseResponse;        // ← API 分支无条件透传

after :  if (!isApi) { !user → redirect("/login") }
         // API 分支：
         if (OPTIONS || isPublicApi(path) || hasAuthCookie(req)) return supabaseResponse;
         if (!user) return 401 JSON;
         return supabaseResponse;
```

**白名单（仅 2 类）**
```
/api/auth/*           认证入口本身 + /api/auth/me（前端登录态探测，未登录返回 401+{user:null}）
/api/feishu/callback  飞书 OAuth 回调：需 302 回前端展示结果，不能替换成 JSON 401
```

### 关键设计取舍

| 取舍 | 决策 | 理由 |
|---|---|---|
| fail-closed 还是降级？ | **降级（fail-safe）** | 一刀切 fail-closed 会在 Supabase 抖动时把正常用户挡成 429；降级保留单实例防护，安全性显著优于放行 |
| 集中鉴权放哪？ | **proxy 链路**，不新建 middleware | `proxy.ts` 的 matcher 已含 `/api/:path*` 且已 `getUser()`；且各 catch-all dispatcher 是 `AUTO-GENERATED ... DO NOT EDIT`，不能手改 |
| 未登录判定多严？ | **只在「明确无 auth cookie」时才 401** | Supabase 抖动导致 `getUser()` 返回 null 时，已登录用户仍带 cookie → 交给 handler 判定，避免全站 API 被误伤 |
| 伪造 cookie 怎么办？ | handler 级 `requireUser()` 兜底 | proxy 只查 cookie 存在性；实测伪造 cookie 可让 originkit 返回 200 → 故补 4 处 handler 鉴权 |
