# 第二大脑 深度体验审计（2026-09-08）

> 本轮审计围绕“作为日常助理是否简单、清晰、快”展开，重点复查高频路径：
> 打开 `/brain`、今日空间操作、进入/返回完整看板、笔记版本回溯、来源/产出回溯、
> 恢复草稿，以及通知/主动简报这类后台扫描是否拖慢前台。

---

## 一、审计结论

核心结论：第二大脑的功能正确性已经有较高覆盖，但“日常助理”体验仍被三层结构问题拖累：

1. **高频路径反复做重活**：多个只读页面服务端整表读取笔记全文/AI struct，
   同一会话又多次重复请求，造成“每次回来都在等”的体感。
2. **视图切换即销毁**：今日空间与完整看板、完整看板内部首页与各工作台之间，
   切换时会卸载组件并重新全量拉取，而不是保留已有内容做静默刷新。
3. **信息架构仍在两个心智之间摇摆**：今日空间已经收敛，但“完整看板”
   内部又复刻一套今日助理，并混入任务、项目、策略、代码片段、数据引擎、复盘等
   高级工具；“即时收录”与“待确认计划”两种保存语义也并存，用户很难形成稳定心智。

## 二、本轮已修复的高频等待项

### H1 版本回溯不再请求后端、且旧版内容可真正查看

审计前：

- 点击展开笔记卡片会调用 `GET /api/brain/notes/:id/versions`。
- 服务端 `listNoteVersions` 内部调用 `listBrainNotes` 全量加载所有笔记，
  但接口只回传 `id/title/version/createdAt/parentId`。
- 前端却把这些轻量对象按完整 `BrainNote` 存入 `versionsByNote`，
  点击时间线圆点后 `content/summary/tags` 实际为 `undefined`，
  也就是“等了很久却看不到旧版内容”。

已修复：

- `components/second-brain.tsx` 的 `loadVersions` 改为从当前已加载的
  `notes` 内存组链，不再发起网络请求；从任意版本卡进入都会完整显示初版到最新。
- `lib/api-handlers/brain/notes/[id]/versions.ts` 改为返回可完整渲染的
  笔记字段，升级接口产生的版本链也不会再是“空壳”。

### H2 今日空间首屏不再整表预取笔记全文

审计前：

- `app/brain/page.tsx` 在服务端无条件调用 `listBrainNotes`，把所有笔记的
  `content`、`struct`、`code_content` 整表读一遍后才渲染“今日空间”。
- 即使用户只是想随手记一条或看最近 10 条，也要为完整看板的未来打开付出全量成本。

已修复：

- `/brain` 页面不再做笔记全量预取；完整看板首次挂载时再客户端拉取。
- `GET /api/brain/today` 改用 `listBrainNoteMetas` 轻量投影，
  只在最近 10 条与待复习卡片涉及的笔记上按 ID 补取正文/struct。

### H3 后端只读聚合接口不再重复搬运大字段

以下接口原本都调用 `listBrainNotes`（含全文/struct/code），已切换为轻量投影或定向查询：

| 调用方 | 原本 | 现在 |
|---|---|---|
| `api-handlers/brain/today` | 全量全文 | metas + 最多十数条定向全文 |
| `api-handlers/brain/dashboard` | 全量全文 | `listBrainNoteMetas` |
| `api-handlers/brain/reviews` | 全量全文 | `listBrainNoteMetas` |
| `brain-reminder.checkReminders` | 全量全文 | `listBrainNoteMetas` |
| `brain-proactive-brief.loadData` | 全量全文 | `listBrainNoteMetas` |

新增 `listBrainNotesByIds`（`lib/brain-db.ts`），供只读详情按 ID 定向加载，
避免“为 10 条详情读取全部正文”。

### H4 今日空间刷新改为“先保留内容，后台替换”

审计前：

- `TodaySpace.load()` 每次设置 `loading=true`，最近的“随手记/复习/摘要”
  会全部退化为骨架屏。
- 即时收录、复习动作、周摘要生成、定时刷新都这样做，用户看到的是
  “页面反复清空再等待”，而非“旧内容还在，新结果悄悄更新”。

已修复：

- `components/brain/today-space.tsx` 支持 `silent=true` 后台刷新；
  已有内容时不清空页面。
- 增加请求序号与卸载清理，避免旧响应覆盖新响应。
- 回到今日空间或发生 `brain:dashboard-refresh` 时静默同步。

### H5 今日空间 / 完整看板切回不再销毁重拉

审计前：

- `BrainHome` 使用 `view === "today" ? <TodaySpace/> : <SecondBrain/>`，
  两个视图互斥卸载；每次从完整看板回今日空间都要重新请求 `/api/brain/today`。
- 完整看板内部首页与工作台切换时，`TodayAssistantPanel`、
  `ProactiveBriefList` 等会随 `topView` 卸载重挂，再次进入首页重新等待。

已修复：

- `components/brain/brain-home.tsx` 采用“首次打开后保持挂载、隐藏而非销毁”的策略。
- `TodayAssistantPanel`、`ProactiveBriefList` 可同步读取会话缓存，
  挂载恢复时不再闪骨架；`brain:dashboard-refresh` 会先失效 30s 缓存再静默刷新。
- `ReminderCenter` 也改为带缓存的轮询，避免每次回看板都重跑一次
  “扫描全库并入队通知”的昂贵 GET。

### H6 恢复/来源回溯改为按 ID 点查，不再全表过滤

审计前：

- `GET /api/brain/plans?id=...` 的 `resolveProduced` 先 `listBrainTasks`、
  `listPendingBrainReminderItems`、`listBrainStrategies` 全量取出再过滤，
  用户只是“恢复一条待确认草稿”也要等待无关数据。
- `buildProvenance` 中按 `noteId`/`planId` 找一条处理计划，却调用
  `listBrainProcessingPlans(undefined, true)` 全量扫描后在内存过滤。

已修复：

- `plans.ts` 改为 `getBrainTaskById/getBrainStrategy/getBrainReminderItem`
  按计划 ID 列表点查。
- 新增 `getBrainProcessingPlanByNoteId` 定向查询；
  `brain-provenance.ts` 对任务先按来源笔记反查计划，常规路径不再全量扫计划。

## 三、仍未解决/建议下一轮处理的问题

### P1 页面级重复心智

1. **三个“每日入口”并存**：`BrainHome` 顶部的今日空间；`SecondBrain` 顶部的
   “首页”（`TodayAssistantPanel`）；还有今日空间右下角“打开完整看板”。
   每个入口的首页内容并不一致，用户需要记住两套界面。
2. **三个输入框语义不一致**：今日空间“即时收录”默认 auto-apply；
   完整看板首页 `QuickCapture` 走“待确认计划”；“记一笔”里又有“直接入库”和
   “帮我整理”两种动作。建议日常助手只保留一种收录心智，
   AI 整理/待确认收敛为可选项或高级工具。
3. **高级工具没有真正“收纳”**：PRD 已明确任务看板、项目管理、表格分析应收进
   “高级工具”，不进入 Brain 首页；当前 `SecondBrain` 的导航仍把首页、记一笔、
   任务看板、项目、策略、代码片段、数据引擎、复盘并排成同一层。

建议：

- 在完整看板内移除第二套“今日首页”，把 `TodayAssistantPanel` 与 `TodaySpace`
  的数据聚合归一为一个 `TodayBrief`。
- 把“任务/项目/策略/片段/表格/复盘”收到折叠的“高级工具”分组，
  默认只显示“记一笔/全部笔记/问我的记忆”。
- 对“即时收录”与“待确认计划”显式加动作标签，并统一为：日常文本默认入笔记；
  会议/任务类内容才进入确认队列。

### P2 数据规模增长后的横向扩展

- `listBrainNotes` 仍会被完整看板使用，笔记数量增长后，
  `/api/brain/notes` 的单次响应会线性膨胀。建议后续把列表改成
  “分页/虚拟滚动 + 展开时按 ID 拉正文”，或至少提供
  `?cursor=`/`?limit=` 服务端分页。
- `listNoteVersions` 仍从全量笔记内存组链；客户端版本回溯已不依赖它，
  但升级接口与旧 API 仍在使用，建议后续改为一次 CTE 或按链内 ID 定向查询。
- `checkReminders` 与 `getProactiveBrief` 仍在同一请求中做多张表的全量扫描，
  建议为“提醒/简报”单独建立每日一次的服务端快照，而不是让每次页面挂载都重扫。
- PG 侧建议为 `brain_processing_plans(user_id, note_id)`、
  `brain_notes(user_id, created_at)` 等新增复合索引，并在
  `pg-schema-reconcile` 中补齐验证。

### P3 隐藏的数据/状态一致性风险

- `TodaySpace` 的 auto-apply 响应返回后，还会用 6s/15s 延迟轮询拉取后台整理结果；
  如果用户在这期间删除该条笔记，后台 `enrichNoteWithOrganized` 可能再补建任务。
  建议后台整理先校验笔记仍存在且仍未被编辑，再回写。
- `SecondBrain` 的笔记列表目前展示所有版本（含 `superseded`）作为独立卡片；
  从产品视角更接近“同一知识的多版本”，当前列表会重复计数并让用户困惑。
  建议列表默认只显示链首，历史版本只在版本时间线内回溯。
- 通知中心 `GET /api/brain/notifications` 实质上有扫描和写库副作用，
  却被当成普通 GET 调用；后续建议拆成“仅读取今日已生成”与
  “定时/显式触发扫描”两个接口，避免 GET 被浏览器或代理缓存语义污染。
