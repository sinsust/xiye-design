## 0. 一句话结论

**工程底座的专业度显著高于产品交付的专业度。** AI 调用层（Prompt 工程、解析容错、幂等、降级标记）已达专业水准；但产品定位「产品需求合成器」的最后一公里是空壳——生成的每个组件都是 `{/* TODO */}`，且 zip 根目录缺 `package.json`。这相当于一位资深 PM 把需求访谈与方案论证做得极专业，最后交给你一份只有标题、没有内容的 PPT 模板。

八个维度加权总分 **6.1 / 10**（详见 §2）。三条最致命缺陷见 §6。

## 1. 审计范围与一个前提纠正

### 1.1 前提纠正：不存在「六阶段」，实际是「4 阶段 + 5 面板」

此前流传的 `concept-brief-panel → blueprint-panel → collab → deliver → refine → build` 把**面板(panel)**与**阶段(stage)**混为一层。真实定义只有 4 个阶段：

```ts
// app/workflow/steps.ts:40-93
export const STEP_DEFS: StepDef[] = [
  { id: "collab",  label: "产品创意", ... },   // :41-53
  { id: "refine",  label: "方案落地", ... },   // :54-66
  { id: "build",   label: "页面搭建", ... },   // :67-79
  { id: "deliver", label: "交付逻辑", ... },   // :80-92
];
```

`concept-brief` / `blueprint` 是 **collab 阶段内的抽屉**，不是独立阶段：

```tsx
// app/workflow/components/concept-blueprint-bar.tsx:15-16 （drawer 引入）
// app/workflow/components/collab-stage.tsx:1325 （挂载 <ConceptBlueprintBar />）
```

同理 `journey / screen-map / screen-spec / prototype` 是 collab 内并排卡片（`collab-stage.tsx:1365,1382,1399,1415`）。

> 阶段组件位于 `app/workflow/components/`；`components/workflow/` 目录仅 `local-draft-hint.tsx` 一个文件。

## 3. Studio 产品线审计

### 3.1 四阶段闭环：✅ 已实现

| 阶段 | 输入 | 处理 | 输出 | AI 参与 |
|---|---|---|---|---|
| collab | 一句话想法 | 5 条收敛链 + 会诊 | conceptBrief / blueprint / journey / screenMap / screenSpec / prototype | ✅ 密集 |
| refine | 上阶段产物 | `/api/ai/panel` 会诊 | techStack / visualStyle + 完善度 | ✅ |
| build | pageBlueprint | 纯本地选取 | pageBlueprint 补全 | ❌ **零 AI** |
| deliver | 全量 store | 纯客户端模板拼装 | GeneratedProject → zip | ❌ **零 AI** |

**门禁设计是专业亮点** —— 判据与阶段内按钮共用同一函数，杜绝"两处规则漂移"：

```tsx

const briefReady = getConceptReadiness(conceptBrief).canProceed;
const refineReady = Boolean(techStack) && Boolean(visualStyle) &&
  refineOverallProgress({ productBrief, visualStyle, techStack, panelOutput }) >= 80;
const buildReady = pageBlueprint.length > 0;
```

被拦截时不静默失败，明示缺什么（渲染于 `page.tsx:526-542`）。

**占位/Stub 扫描**：`app/workflow/components/*.tsx` grep `TODO|FIXME|mock|占位|敬请期待` 仅 3 处命中且全为描述性文案（`build-stage.tsx:75,263,286` 讲"占位文案联动"）。**无死按钮**。

### 3.2 AI 调用层：🟢 专业度高

**Prompt 工程质量优秀**（`lib/ai-concept-server.ts:24-71`）：
- 角色设定（`:24`）"你是一位资深产品负责人…有判断的产品访谈，不是问卷"
- 强格式约束（`:63-64`）"只能输出一个 JSON 对象，禁止任何前后解释、markdown 代码块"
- 内联 JSON Schema 与空值占位（`:65-71`）
- **反幻觉负面约束**（`:49-52`）：
  ```
  严禁生成技术栈/数据库/框架/部署方案…
  严禁编造目标用户、成功指标、市场数据…
  严禁用「泛泛假设」填满空缺字段；宁可留空并进 openQuestions。
  ```

**解析容错三层防御**（`lib/ai-concept-server.ts:97-146`）：直接解析 → 提取代码块并修尾逗号 → 括号平衡截取（抗截断）。再叠加逐字段归一化（`lib/flow-concept.ts:361-389`），缺字段回落空值，绝不让 `undefined` 泄漏到渲染层。

**幂等防重复计费**（`lib/api-handlers/ai/concept-brief.ts:134-139`）：操作级幂等 `getFlowOpResult` + `applyFlowOpOnce`，并发重试命中唯一索引即返回已存结果。

**失败语义诚实**（`concept-brief.ts:175-191`）：失败保留旧 Brief、不清空用户内容，返回结构化错误码 `provider_unavailable` / `invalid_response` / `unknown`。降级黄标 `components/ai-fallback-badge.tsx:13-30` 在 3 处真实挂载（`chat-stream.tsx:481`、`collab-stage.tsx:1321,1491`、`refine-stage.tsx:317`）。

## 8. 迭代建议：三批次路线图

> 排序依据：先堵「用户第一分钟就撞到的墙」，再补「定位兑现」，最后才做「体验打磨」。
> 这与 PRD §10 的 RICE 结论一致——**M2 交付闭环优先级最高**。

### 批次 P0 · 止血（本轮，预计工作量小、收益极大）

| # | 动作 | 文件 | 说明 |
|---|---|---|---|
| P0-1 | **四处 `rewritten \|\| content` 改用 `withOriginal()`** | `second-brain.tsx:1401,1830`、`ima-brain.ts:117,186`、`import/batch.ts:61,74` | 复用 `lib/brain-plan.ts:66-68` 已有函数，一处导入即可。彻底堵死原文丢失 |
| P0-2 | **zip 根目录补 `README` 首行指明 `cd seed/`**，或把 `package.json` 提到根 | `lib/project-generator.ts:972-987` | 二选一。推荐后者：交付物根目录即工程根，符合 PRD §6.3「WorkBuddy 直接打开目录」 |
| P0-3 | **首页加 Brain 入口** | `app/page.tsx:772-790` | 与 Studio 区块对称，加一个 Brain 区块（今日空间 + 记忆检索），兑现「两条清晰主线」 |
| P0-4 | **删除死代码 `more-tools-panel.tsx` 或改造成真·高级工具** | `components/more-tools-panel.tsx` | 当前内容名不副实且无人引用 |
| P0-5 | **InboxDrawer 单条提交护栏** | `components/InboxDrawer.tsx:150` | 空行拆分前提示"将拆成 N 条"，或默认不拆（仓库审计文档自认的 P3 回归风险） |

### 批次 P1 · 定位兑现（核心，决定产品成立与否）

| # | 动作 | 说明 |
|---|---|---|
| P1-1 | **业务专属功能页生成器** | 这是「产品需求合成器」与「视觉模板拼装器」的分水岭。需要：① 从 `project-types.ts` 的业务维度（下单/预约/交易/评价）派生**带状态与数据流**的页面（接单列表 → 订单详情 → 服务详情）；② 生成的不只是 `<section>` 占位，而是含 mock 数据流、状态机、表单校验的可运行页 |
| P1-2 | **build 阶段引入 AI** | build 阶段此前仅在「一键改写全站文案」处有 AI（经 `fetchSiteCopyOverride` 封装，故直接 grep `fetch(` 计数为 0 属**统计口径误差**，非真无 AI）；但右栏「AI 协同建议」是硬编码静态文案，点了没反应。应补上基于选中区块的真实 AI 建议 |
| P1-3 | **deliver 阶段的产物智能** | 当前是纯客户端模板拼装。至少让 AI 参与"代码契约"生成（`xiye.agent.json`），而非静态填充 |
